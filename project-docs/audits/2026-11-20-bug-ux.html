B1

A free user who opens the app offline more than 48 hours after the last good load sees an empty board that says 'Showing saved data'

mediumconfirmedstate
Impact

The screen claims saved data is being shown while it shows nothing, and the only action is Retry. A free user who opens the app on a plane, in a stadium with poor signal, or after a few days away sees a broken app on the first screen. Followed players and Teams are empty too. Pro users are moved to 2025 and are not affected.

How it happens
  1. Free user (no StatScout+) has used the app, then does not open it for more than 48 hours (or iOS purges Caches, or this is a first launch with no signal).
  2. Open the app in airplane mode or with a feed that times out.
  3. load() finds no readable current-season file (PlayerCache.swift:24-30 throws once the file is older than 48 hours), the request throws URLError, and only the bundled 2015-2025 history is ingested.
  4. The selected season stays 2026 because a free user may not be moved to a locked past season (DashboardViewModel.swift:1346-1352).
  5. Stats tab shows the 'Data Error' card with the text 'Showing saved data. Pull to refresh when your connection improves.' and no players at all.

B4

On a phone set to a non-Gregorian calendar (Japanese, Islamic, Persian, Taiwan; Buddhist in places) dates from the server land centuries off

lowconfirmeddata
Impact

Date.fromPostgresDate builds DateComponents(year: 2026, month: 9, day: 27) in Calendar.current. On a non-Gregorian calendar the year 2026 is a different year (Buddhist 2026 is 1483 CE, Japanese 2026 is 4044 CE, Islamic 2026 is about 2584 CE). Every as_of and game-through date is then centuries off. Results: (1) Pro Recent Form on Islamic, Japanese, Persian, Taiwan and Hebrew calendars uses an anchor in the far future, min() falls back to now, the cutoff is rebuilt from now's local year number (for example Japanese year 8) as a Gregorian year, so the cutoff is year 8 AD and every game of the season passes the filter. The window is labelled 15 days but holds the whole season, so the numbers are wrong. (2) Settings 'Games Through' shows a day count in the hundreds of thousands (past dates) or negative (future dates). (3) slidWindowStart shifts the team-form request back by about 540 years on Buddhist phones, so team cards download the entire season instead of 37 days. (4) The default selectedSeason is calendarYear(), which is 2569 on a Buddhist phone; it self-heals after load, but the first paint is for a season that does not exist.

How it happens
  1. On an iPhone set Settings > General > Language & Region > Calendar to Islamic (Umm al-Qura) or Japanese (Thai and Saudi region phones default to Buddhist and Islamic). Leave the app in English.
  2. Sign in as a StatScout+ subscriber, open any player profile during the season, and pick the Recent view (Last 15 days).
  3. The 'Last 15 days' bars are built from the player's whole season of games, not 15 days.
  4. Open Settings > Data. On a Buddhist-calendar phone 'Games Through' reads like 'Sep 27 (197000 days ago)'.
Where
StatScout/Models/RecentForm.swift:10StatScout/Models/PlayerGameLog.swift:181StatScout/Services/StoreService.swift:50StatScout/Views/SettingsView.swift:192
Suggested fix

Parse Postgres dates with a Gregorian calendar (Calendar(identifier: .gregorian) with the local time zone) and do the 'same day' arithmetic on a Gregorian calendar everywhere. Make StoreService.calendarYear and the profile-window component read use Gregorian too. Add the four tests as regression tests.

Evidence
static func fromPostgresDate(_ raw: String, calendar: Calendar = .current) -> Date? {
    let bits = raw.split(separator: "-").compactMap { Int($0) }
    guard bits.count == 3 else { return nil }
    var parts = DateComponents()
    parts.year = bits[0]
    parts.month = bits[1]
    parts.day = bits[2]
    return calendar.date(from: parts)
}
// PlayerGameLog.swift:181-189
var eastern = Calendar(identifier: .gregorian)
eastern.timeZone = PlayerGameLog.gameDateZone
let day = calendar.dateComponents([.year, .month, .day], from: anchor)
guard let anchorDay = eastern.date(from: day), ...

The Postgres string is a Gregorian date, so it must be parsed with a Gregorian calendar. The profile-window function then mixes two calendars: it reads year/month/day from the device calendar and feeds them to a Gregorian calendar. For a Buddhist phone the two mistakes happen to cancel when the anchor came from fromPostgresDate, which is why the window looks right there, but not when the anchor is .now (recentAnchor nil) or on any other non-Gregorian calendar. Existing tests (ClockBoundaryTests) only use Gregorian calendars in different zones. Other code already knows to use an explicit Gregorian calendar: SavantModules.swift:66 does.

Checked by: Swift script run on this Mac: the date 2026-09-27 built in a Buddhist calendar is Gregorian year 1483, Japanese 4044, Islamic 2587, Persian 2647, Taiwan 3937. Date.fromPostgresDate (RecentForm.swift:10) builds exactly that with Calendar.current.

Not proven: How many customers use these calendar settings is unknown; it is likely very few for a US baseball app, which is why this is ranked low.

B5

A cancelled recent-form fetch clears the loading flag and task handle of the fetch that replaced it

lowconfirmedstate
Impact

For the seconds the second request runs, the Trends board says there is nothing to rank instead of showing a spinner; a duplicate request is fired by any caller that arrives in that gap (HotColdView.task, window picker). It clears itself when the new request ends.

How it happens
  1. Open the Trends (Hot/Cold) tab as a Pro user so a window fetch is running, on a slow connection.
  2. While it is still loading, trigger a reload of the same window (the Try Again button after an earlier error, or the foreground refresh that rebuilds held windows).
  3. reloadRecentForm cancels the old task, removes its handle, and starts a new fetch.
  4. The old task unwinds on cancellation and its defer removes that window from recentFormLoadingWindows and removes the dictionary entry, which now belongs to the new task.
  5. The new fetch is still running, but the board shows 'No movement to rank yet' instead of the loading state, and a third caller starts another request instead of joining.
Where
StatScout/ViewModels/DashboardViewModel.swift:558StatScout/ViewModels/DashboardViewModel.swift:532
Suggested fix

In the defer only clear the entry if recentFormTasks[key] is still this task (compare a generation token), with a per-request token.

Evidence
let task = Task { @MainActor [weak self] in
    guard let self else { return }
    defer {
        self.recentFormLoadingWindows.remove(target.rawValue)
        self.recentFormTasks.removeValue(forKey: target.rawValue)
    }

Both removals are keyed by window, not by which task owns the entry. The caller inserts the new entry synchronously before the old cancelled task gets to resume on the main actor, so the old defer always runs after the new insert. I checked the three paths that cancel (reloadRecentForm, refreshCachedRecentFormWindows, a flipped window): the first two re-enter loadRecentFormIfNeeded for the same key.

Checked by: Code reread: the cancelled task's defer (DashboardViewModel.swift:558) removes the loading flag and task handle by window number, so it removes the ones the replacement fetch just set. The proof test was written but never ran.

Not proven: Test written, not run (queue). Reachability is narrow: it needs a reload while the same window is still fetching.

B7

A foreground refresh can cancel an in-flight Trends window fetch it does not restart, leaving 'No movement to rank yet' on a board that never loaded

lowplausiblestate
Impact

Rare and self-healing, but the empty message is wrong (it blames the stat, not a cancelled load). Also the presubmit P2 still open: the cancelled task's defer removes the replacement task's entry and loading flag.

How it happens
  1. Pro user has Trends open with the 15 day window loaded, then backgrounds the app overnight.

  3. load() sees a newer coverage date, calls refreshCachedRecentFormWindows(), which cancels every task in recentFormTasks, including the new 30 day fetch, but only re-requests windows that already had data (15).
  4. The cancelled 30 day task reports no error and sets no data; the board shows 'No movement to rank yet'. Switching tabs away and back re-asks and recovers.

Suggested fix

recentFormTasks.removeAll()
