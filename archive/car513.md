# StatScout App Store Review — Critical Findings

## 1. Premium Features & Paywall Design

### What's Locked Behind Pro
- Historical seasons (anything ≠ 2026)
- Year-over-Year comparison
- Player vs. Player comparison
- Past season data loading

### Paywall Density
There are **7 distinct paywall triggers** scattered across the app:
1. pastSeason — tapping a non-current year
2. yearCompare — tapping Year Compare tab
3. playerComparison — tapping compare button
4. onboarding — final onboarding card
5. upgrade — toolbar Pro button / upsell banners
6. pastSeasonsLoad — loading historical data
7. teamView — team season menu

**⚠️ Risk:** 7 entry points to the same paywall is aggressive. Reviewers may flag this as overly persistent upselling, especially on a free app with no ads. The blurred previews + CTAs for Year-over-Year and Player Comparison are the highest-risk patterns — gating features behind blurred overlays frustrates users.

### Three Products, One Entitlement
- Monthly ($X.99/mo)
- Yearly ($X.99/yr, with free trial)
- Lifetime ($XX.99)

**⚠️ Risk:** No consumables, no ads, no free trial gating — this is relatively clean. But the value proposition is thin: the free tier already gets the current season, which is what most casual fans want. Pro unlocks are back-catalog features. Reviewers may question whether the perceived value matches the price point.

### RevenueCat SDK
- Uses `purchases-ios` v5.72+, API key hardcoded: `appl_qNlZGCCfGWBTsvcxlqYSNCtRupx`
- Customer info refreshed on every foreground event
- StoreKit 2 fallback via `StoreManager`

**⚠️ Risk:** Hardcoded API keys are generally acceptable for RevenueCat (public SDK key), but ensure it's not exposed in a way Apple flags.

## 2. MLB Brand & Data Usage — MAJOR CONCERN

### The Core Problem
This app is entirely built **on top of MLB's data ecosystem**:

| Asset | Source | How It's Used |
|---|---|---|
| Player stats | MLB Stats API (`statsapi.mlb.com`) | Every player profile, every season |
| Statcast metrics | pybaseball → Baseball Savant | All percentile rankings |
| Player headshots | `midfield.mlbstatic.com` CDN | Every player profile image |
| Player links | `baseballsavant.mlb.com` | Every "View on Savant" button |
| Team links | `baseballsavant.mlb.com/team/{abbr}` | Team views |
| Team names/abbr | MLB trademark | Core navigation |
| Team colors | Approximated RGB | UI dots/badges |
| Standard stats | Baseball-Reference (via pybaseball) | Secondary stats view |

### Disclaimer Coverage
A non-affiliation disclaimer appears in 3 places:
- In-app `AboutView.swift`
- `docs/terms.html` (Terms of Use)
- App Store description in `APP_STORE_SUBMISSION.md`

### 🚩 RED FLAGS

**1. Visual emulation of Baseball Savant**
The design handoff explicitly states the app mirrors Baseball Savant's visual conventions (navy slabs, red accents, percentile bars, typography). The handoff claims "permission from MLB," but **this needs independent verification** — an App Store reviewer will notice the resemblance immediately and may reject for trademark/trade dress infringement.

**2. MLB trademarks throughout**
- Team names (Yankees, Red Sox, etc.) are MLB trademarks used for identification — this is usually ok if disclaimed, but the app uses them as primary navigation structure
- Player names and likenesses may trigger MLBPA concerns if monetized
- "Statcast" is trademarked by MLB Advanced Media and appears throughout the app

**3. API ToS compliance**
- `statsapi.mlb.com` — MLB SportsData API has terms of service restricting commercial use. If money is being made (subscriptions), this could violate their ToS.
- `midfield.mlbstatic.com` — Hotlinking to MLB's image CDN in a paid app is risky. MLB can block this at any time and may consider it unauthorized commercial use of their assets.
- `baseballsavant.mlb.com` — Linking out is fine, but scraping data via pybaseball to power a paid app is legally questionable.

**4. "Statcast" in the data pipeline**
pybaseball scrapes Baseball Savant (which is MLB.com property). Using Statcast percentile rankings as the core value proposition of a paid app is essentially **reselling MLB's analytics product** with a nicer mobile wrapper.

**5. GitHub Actions nightly ingestion**
The backend runs a nightly job that:
- Scrapes MLB's statcast data
- Calls MLB Stats API for standard stats
- Aggregates into Supabase

This is systematic, automated, and commercialized — far removed from "personal use" of public APIs.

## 3. App Store Compliance Concerns

### Guideline 4.1 — Copycats
The visual similarity to Baseball Savant is the #1 rejection risk. Apple rejects apps that look like existing branded products. If a reviewer recognizes the Baseball Savant design language, this is a rejection.

### Guideline 5.1.1 — Data Collection
✅ Actually clean here — no accounts, no tracking, no analytics SDKs beyond RevenueCat (which doesn't collect user data for tracking).
✅ No IDFA, no third-party ads, no social logins.

### Guideline 3.1.1 — IAP / Paid Content
⚠️ Moderate risk. The app reads data from an external API, caches it, and unlocks features. This is fine as long as:
- The data isn't content that users paid MLB for (debateable)
- Subscriptions don't gate core functionality (arguable — current season is free)

### Intellectual Property Infringement (Apple's standard)
If MLB submits a complaint, Apple will pull the app immediately. **The question isn't whether MLB could complain — it's whether they will notice.** Given that:
- App Store search keywords include "mlb"
- MLB actively police trademark misuse
- The app has 7 paywall triggers showing blurred data from MLB's API

...the risk is **non-trivial**.

## 4. Recommended Actions Before Submission

### High Priority
1. **Document MLB API ToS compliance** — Confirm that commercial use of `statsapi.mlb.com` is permitted under their terms, or switch to an alternative
2. **Replace or proxy MLB headshots** — Either cache images locally with attribution, or use a non-MLB source
3. **Diversify the visual language away from Savant** — This is the most likely rejection reason. Change nav bar colors, percentile bar styling, and typography to be clearly distinct
4. **Verify the "permission from MLB" claim** — Get written documentation if it exists; if it doesn't, assume it's not real and redesign accordingly

### Medium Priority
5. **Remove "Statcast" branding** — References to Statcast (a trademarked MLB term) should be replaced with generic equivalents ("advanced metrics", "percentile rankings")
6. **Add attribution for data sources** — "Powered by MLB Stats API" (if ToS allows) or clearly state data sources in the app
7. **Reduce paywall density** — 7 entry points is aggressive. Consolidate to 3-4 maximum to avoid review rejection

### Low Priority
8. **Remove "mlb" from App Store keywords** — Drawing attention isn't helpful if there's a trademark concern
9. **Consider MLB's public data policy** — MLB Advanced Media allows non-commercial use of public data. The subscription model may push this outside that boundary

---

## 5. Overall Verdict

**Risk Level: MODERATE-HIGH**

The app is well-architected, privacy-conscious, and has solid technical foundations. But it has two existential risks:

1. **App Store rejection** due to Baseball Savant visual similarity (likely)
2. **IP/trademark complaint** from MLB if the app gains visibility (possible)

The subscription model while using MLB's APIs and CDN is the fundamental tension — the app is monetizing data that MLB provides for free. If the reviewer notices the Savant resemblance, the app will be rejected. If it gets through and gains traction, MLB legal may step in.

The disclaimers help but don't eliminate the risk, especially when the app's entire visual identity and data pipeline are built on MLB's ecosystem. The safest path is a visual redesign away from Savant conventions and explicit confirmation of data source licensing terms.
